Ce document explique exactement ce que l'application fait sur le réseau, comment vérifier toi-même que rien ne fuit, et comment activer le mode hors-ligne strict si tu veux une garantie active côté navigateur.

🎯 La promesse en une ligne

MyKTAMap est une application 100 % client-side. Aucune de tes annotations, sessions, plans ou données personnelles n'est jamais envoyée à un serveur, ni à un service tiers. Point final.

C'est vérifiable par toi-même sans avoir à nous croire sur parole — la suite du document t'explique comment.

  • du code de tracking ajouté (analytics, fingerprinting)

Comment t'assurer que tu es sur le vrai site ?

  1. Vérifie l'URL dans la barre d'adresse de ton navigateur
  2. Elle doit commencer par https://myktamap.fr ou https://dev.myktamap.fr
  3. Vérifie que le cadenas 🔒 est présent (HTTPS valide, certificat émis par Let's Encrypt)
  4. Si l'URL ne correspond pas, tout ce qui est écrit dans cette page ne te concerne pas — c'est une copie tierce sur laquelle nous n'avons aucun contrôle

NB : pour les utilisateurs qui veulent self-héberger MyKTAMap (cas légitime — c'est tout l'intérêt d'un code open source), c'est parfaitement autorisé sous la licence. Mais dans ce cas, c'est toi qui es responsable de garantir l'intégrité de ta propre installation à tes utilisateurs.

🏛️ Le modèle technique (en bref)

MyKTAMap est une Progressive Web App (PWA) servie comme un site web statique. Concrètement :

ComposantRôleStockage
Ton navigateur Exécute tout le code de l'app, gère l'interface, fait les calculs (pathfinder, export PNG, KMZ…) localStorage + IndexedDB (uniquement local)
Notre serveur Nginx Sert les fichiers statiques de l'app (HTML, JS, CSS, images, plans serveur de démo) Aucune base de données, aucune session utilisateur

Pas de backend applicatif. Pas de base de données serveur. Pas de compte utilisateur. Pas de session côté serveur. Pas de cookies de tracking. Pas d'analytics tiers (Google Analytics, Matomo, etc.). Pas de CDN tiers.

Tout ce que tu crées dans l'app (points, tracés, zones, sessions, plans mémorisés, calibrations KMZ, préférences) reste dans ton navigateur, dans des espaces de stockage isolés à ton appareil (localStorage et IndexedDB).

À propos du ping <origin>/ping.html (depuis v1.9.3)

Avant v1.9.3 : l'app utilisait https://www.gstatic.com/generate_204 (endpoint Google) pour détecter Internet. Depuis v1.9.3, l'app utilise uniquement un fichier /ping.html servi sur le même domaine que l'app (same-origin) :

  • Prod : https://myktamap.fr/ping.html
  • Dev : https://dev.myktamap.fr/ping.html

L'URL est résolue dynamiquement via location.origin + "/ping.html".

🔎 Contrôle du 13/09/2026 — aucune URL de service n'est codée en dur. Tous les appels de l'app (version.json, alert.json, denylist.json, data/index.json, lang/*.json, ping.html, licence pro) sont relatifs à l'origine qui sert l'app ; la seule cible externe écrite en dur est tile.openstreetmap.org (Vue OSM). C'est voulu : une copie servie ailleurs (self-host, kiosque, copie tierce) appelle sa propre origine et jamais myktamap.fr — elle ne reçoit ni nos alertes, ni notre liste de révocation, ni nos mises à jour, et nous ne recevons rien d'elle. La garantie ci-dessus ne vaut donc que pour le domaine officiel : elle porte sur le code servi, que seule la barre d'adresse permet de vérifier.

Le body attendu est exactement "OK".

Pourquoi ce changement ? Plus aucun appel externe vers un service tiers, même bénin comme Google. Le ping same-origin permet en outre de vérifier en un seul appel :

  • Connexion Internet active (DNS résout, route IP atteignable)
  • Certificat SSL du domaine valide
  • Serveur Nginx en ligne et répond correctement
  • La PWA peut tenter le pull SW (skipWaiting + cache purge)

L'app l'appelle en mode same-origin (default) avec credentials: "omit" : aucun cookie n'est envoyé, et seul le body "OK" (texte brut) est lu pour vérification. Si le serveur répond autre chose (404, 500, body différent), le ping est traité comme "indispo" et l'app refuse de tenter la mise à jour douce.

Si tu préfères ne pas faire ce ping du tout, active le mode hors-ligne strict (cf. plus bas) : il sera bloqué comme tout autre appel non local.

À propos des tuiles OSM tile.openstreetmap.org (depuis v1.39.0)

Avant v1.39.0 : l'app n'avait aucun appel sortant vers un domaine tiers, strictement same-origin + ping /ping.html. Depuis v1.39.0, l'app peut contacter tile.openstreetmap.org pour afficher la carte OSM uniquement sous 3 conditions strictes simultanément réunies :

  1. Le plan a un georef GPS (saisi via générateur avancé OU via Réglages map mode → Géoréférencement). Sans georef, le bouton 🗺️ Vue OSM est masqué côté UI et l'appel n'a aucun moyen de se déclencher.
  2. L'utilisateur a activé le toggle « 🗺️ Autoriser la Vue OSM » dans ⚙️ Configuration home. Default OFF, persisté en localStorage sous la clé myktamap_osm_view_opt_in. L'utilisateur peut le désactiver à tout moment.
  3. L'utilisateur charge effectivement la Vue OSM. Deux contextes possibles depuis v1.40.0 (= roadmap Step 4 Vue OSM HOME) :
    • Modale Vue OSM full-screen (mode carte) : clic sur le bouton 🗺️ dans la status bar quand un plan est chargé. Couvre les tuiles plan V2 projetées + POI + Tracker + Roads + Iti + Zones + Structures.
    • Widget mini-preview HOME (page d'accueil) : si l'opt-in est ON, la colonne 🌍 Vue OSM apparaît entre Mes plans et Ajouter, avec un plan georef sélectionné par défaut (= lastOpened). Sinon la colonne est masquée entièrement — aucune tuile OSM n'est requêtée même visuellement.

Garanties supplémentaires :

  • Le bouton modale et la colonne widget sont aussi masqués si « Mode hors-ligne strict » OU « Mode incognito » sont actifs (extension automatique de ces deux modes).
  • Modale et widget : masqués si navigator.onLine === false (hors-ligne détecté par le navigateur).
  • Un ping /ping.html est effectué juste avant l'ouverture de la modale Vue OSM : si Internet ne répond pas, la modale est annulée AVANT le premier appel à OSM.
  • Les requêtes vers OSM sont faites en mode cors standard avec crossOrigin: true côté Leaflet (cookies omis par défaut). Aucune donnée utilisateur n'est envoyée : juste les coordonnées géographiques {z}/{x}/{y} de la tuile, c'est-à-dire un quadrillage Web Mercator standard partagé par tous les utilisateurs OSM.
  • Cache PWA (jusqu'à v1.42.x) : les tuiles OSM n'étaient PAS mises en cache par le Service Worker — elles ne survivaient pas au plan switch ni au refresh. Comportement modifié depuis v1.43.0 : un cache offline OSM opt-in user (bouton « 💾 Cacher pour offline ») a été ajouté. Détails complets dans la sous-section dédiée plus bas (« Cache offline OSM (depuis v1.43.0) »).
  • Widget HOME (depuis v1.40.0) : extraction du ZIP du plan sélectionné se fait localement dans le browser via JSZip (lecture IDB blob ou FS handle). Aucune donnée plan n'est envoyée à OSM ou à un tiers — uniquement les tuiles {z}/{x}/{y} sont demandées au CDN OSM, identiques à celles affichées par tout client OSM standard.
  • Bouton « 📍 Ma position » (depuis v1.40.18) : disponible dans la modale Vue OSM ET dans le widget HOME Vue OSM. Fix GPS ponctuel à la demande user via navigator.geolocation.getCurrentPosition() — pas de watch continu (watchPosition), pas d'usage batterie en continu. La permission OS est demandée à la demande user (pas au boot), les coordonnées sont affichées sur la carte (marker bleu cyan + cercle d'incertitude) uniquement en RAM, ne sont jamais stockées en localStorage / IndexedDB / cookie, ne sont jamais envoyées sur le réseau (aucun fetch, aucun beacon). Au close de la modale / refresh du widget, le marker est supprimé. Re-clic = nouveau fix, l'ancien est remplacé.
  • Garde-fou « GPS hors champ du plan » (depuis v1.40.21) : après un fix GPS reçu, si la position est très loin de la bbox du plan georef sélectionné (>50% au-delà des bords), le marker n'est pas affiché + toast warn avec la distance approximative au centre du plan. Garantit qu'un user à Paris ne voit pas son fix s'afficher sur un plan des Catacombes de Lyon par erreur. Marge ×1.5 (= bounds.pad(0.5)) choisie permissive pour ne pas rejeter les fix légitimes en bordure de plan. Si la bbox plan n'est pas calculable (dims manquantes, georef absente), fallback safe : on autorise (comportement v1.40.18-20 préservé).
  • Header serveur requis (depuis v1.40.20) : pour que le bouton 📍 fonctionne, le header Permissions-Policy côté Nginx doit autoriser geolocation=(self). Si le header est resté à geolocation=() (default v1.0-v1.40.19), l'API rejette l'appel avant même le prompt OS avec une violation policy (crbug.com/414348233). La config Nginx versionnée (docs/nginx-csp-config.conf et docker/nginx-docker.conf) a été mise à jour. Restriction (self) choisie volontairement : seule notre origine peut utiliser l'API, JAMAIS un iframe tiers (même si l'app n'en charge aucun).
  • Gating Mode hors-ligne strict + Mode incognito (depuis v1.40.19) : la Vue OSM (modale ET widget HOME) respecte les modes vie privée :
    • Mode hors-ligne strict activé → modale bloquée à l'ouverture (toast warn) + widget HOME affiche un message dédié "🛡️ Hors-ligne strict actif" au lieu de la mini-carte (parité ajoutée v1.40.19, le widget avait un trou v1.40.0-18).
    • Mode incognito activé → idem (message "🕶️ Mode incognito actif" dans le widget HOME, modale bloquée).
    • Bouton « 📍 Ma position » : si l'user active strict offline ou incognito PENDANT que la modale est ouverte (edge case toggle pendant session), le bouton est désactivé visuellement (au build initial) ET le clic est neutralisé runtime (toast warn + early return, jamais de fix GPS). Note : navigator.onLine === false (Wi-Fi/4G coupé) n'empêche pas le GPS — c'est l'intérêt principal (téléphone en avion mais GPS du device parfaitement fonctionnel).

    Le mode Avion coupe le WiFi/4G/5G entièrement. Tu peux donc faire des recherches web en parallèle pendant que MyKTAMap reste isolée.

    🔐 La Content Security Policy (CSP)

    En plus du module d'audit côté JS, le serveur Nginx envoie un en-tête HTTP Content-Security-Policy qui demande à ton navigateur de bloquer toute tentative d'envoi de données vers un domaine non autorisé.

    C'est une double protection : même si un attaquant injectait du code malveillant dans une dépendance, ton navigateur lui-même refuserait l'envoi.

    Tu peux vérifier la CSP appliquée :

    1. F12 → onglet Network
    2. Recharge la page
    3. Clic sur la première requête (le HTML de la page)
    4. Onglet Headers → cherche Content-Security-Policy

    La directive clé est connect-src 'self' blob:; — le navigateur n'acceptera pas d'envoyer des données ailleurs.
