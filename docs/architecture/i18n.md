# i18n — Internationalisation (multi-langue)

> Chantier démarré en **v1.45.0**. Objectif : extraire tout le texte user-facing codé en dur en français vers des dicos `lang/<code>.json`, pour pouvoir ajouter EN/ES/RU/… sans toucher au code moteur.

## 🎯 Principe

- **Source de vérité** : `js/langManager.js` expose `window.I18n`. C'est le SEUL point d'accès aux traductions.
- **Dicos plats par clés** : `lang/fr.json`, `lang/en.json`, … Chaque entrée = `"module.section.element": "texte"`. Pas d'objets imbriqués (clés plates = diff Git lisible, recherche triviale, parité vérifiable d'un `Object.keys`).
- **FR = langue de référence ET fallback universel** : `lang/fr.json` est TOUJOURS chargé. Toute clé absente d'une autre langue retombe sur le FR. Toute clé absente PARTOUT retourne la **clé brute** (visible à l'écran = signal de dette, jamais de crash).
- **Migration progressive, vague par vague** : on remplace `"Texte FR"` par `I18n.t("cle")` module par module. Un module non-migré garde son FR inline (correct). Un module à moitié migré marche aussi. **Aucune régression possible.**

### HTML statique : attributs `data-i18n` (HOME)

Pour les zones **HTML statiques** (l'écran d'accueil `#planLoaderOverlay` dans `index.html`), on n'appelle pas `I18n.t()` à la main : on **annote le DOM** et un applieur générique remplace le texte depuis le dico.

| Attribut | Effet |
|---|---|
| `data-i18n="clé"` | remplace `textContent` par `I18n.t("clé")` |
| `data-i18n-html="clé"` | remplace `innerHTML` (valeurs avec `<strong>`, `<br>`…) |
| `data-i18n-title="clé"` | pose `title` + `aria-label` = `I18n.t("clé")` |

`main.js > _applyI18nDom(root)` parcourt ces attributs et applique le dico. Appelé **au boot** (après `I18n.init`, le HOME est déjà dans le DOM) et **à chaque changement de langue**. Le texte FR laissé dans le HTML n'est qu'un **fallback** (FR = référence) ; la vraie source reste `lang/<code>.json`. Ajouter une langue au HOME = rien à coder, juste le dico.

**Sélecteur HOME** : `<select id="loaderAppLang">` dans la modale **⚙️ Configuration du HOME** (`#loaderLangSection`, juste après le bloc Incognito — **déplacé du header en v1.46.1**, header trop chargé sur mobile), peuplé par `main.js > _initHomeLangSelect()` depuis `I18n.available()` (options = drapeau + label complet). Au change : `I18n.setLang()` + `_applyI18nDom(document)` **en place** (pas de reload → re-traduit le HOME **et la modale ouverte** ; compatible **incognito**, qui réutilise le même écran HOME).

> 🩸 **RÈGLE (v1.85.4, payée par un bug visible) — jamais de HTML dans une clé rendue en TEXTE.**
> `config.batterie.label` et `config.display.vibration.label` portaient la mention `<em>(s'applique à tous tes plans)</em>` **dans la valeur du dico**. Côté mode plan la clé part dans un gabarit `innerHTML` → rendu correct. Côté HOME elle est posée par `data-i18n` → `textContent` : l'utilisateur a vu `🔋 Niveau de batterie <em>(s'applique à tous tes plans)</em>`, balises comprises. **Une même clé, deux canaux de rendu, un seul qui pardonne.**

Le balisage se met dans le **gabarit**, jamais dans le dictionnaire (ici : une clé à part, `config.scope.tousPlans`, ajoutée par `interfaceConfig.js` seul).

## 🧩 API publique (`window.I18n`)

| Méthode | Retour | Usage |
|---|---|---|
| `init()` | `Promise` | Précharge fr (fallback) + langue active. **À await au boot** (fait dans `main.js`). |
| `t(key, params)` | `string` | Traduction : langue active → fr → clé brute. `params` = objet `{nom: val}` pour interpoler `{nom}`. |
| `getLang()` | `"fr"`\|`"en"`\|… | Langue active courante. |
| `setLang(code)` | `Promise` | Change + persiste (clé partagée) + fetch le dico si besoin + notifie les abonnés. |
| `ensureLang(code)` | `Promise` | Charge un dico (lazy) sans changer la langue active. |
| `onChange(cb)` | `unbind()` | S'abonner aux changements de langue (re-render des modales ouvertes). |
| `reload()` | `Promise` | Vide le cache mémoire des dicos + refetch frais (`cache:"reload"`) + notifie `onChange`. Utilisé au **swap SW passif** (cf. ci-dessous). |
| `available()` | `[{code,label,flag}]` | Langues déclarées. |
| `resolveContentLang(liste)` | `"fr"`\|`"en"`\|… | Langue à présélectionner pour un contenu dont les langues dispo sont `liste` : langue app si dispo, sinon `en`, sinon `fr`. Ne lit pas `myktamap_readme_lang`. |
| `has(key)` | `bool` | La clé existe-t-elle (langue active OU fr) ? |

### Interpolation

```js
// lang/fr.json :  "iti.distance": "Distance : {dist} m"
I18n.t("iti.distance", { dist: 42 });   // → "Distance : 42 m"
```

## 🚀 Chargement au boot

1. `index.html` charge `<script src="js/langManager.js">` **tôt** (juste après `copyright.js`). Au load, langManager.js ne fait QUE définir `window.I18n` — aucune requête, aucune écriture storage.
2. `main.js` (`initApp`) fait `await window.I18n.init()` **avant** `_splashStart()` / `lancerApplication` → les dicos (fr + langue active) sont prêts avant tout rendu d'UI/modale.
3. `sw.js` précache `./js/langManager.js` + `./lang/fr.json` + `./lang/en.json` (`ASSETS_TO_CACHE`). `langManager.js` + `fr.json` sont en plus dans le **shell critique** (`CRITICAL_APP_SHELL`, retry x3) → boot offline correct dès le 1er install.

Échec réseau d'un dico → `_loadDict` résout `{}` (jamais reject) → fallback FR garanti.

**Fraîcheur des dicos (anti-périmé).** `_loadDict` fetch `lang/<code>.json?v=<build>` (cache-buster par version, v1.46.6) en **`cache:"reload"`** (v1.47.0) : force un GET réseau qui **ignore le cache HTTP navigateur** au lieu de seulement le revalider — sans ça, un `304 Not Modified` sur l'URL `?v=` figée (build inchangé en cours de cycle de dev) pouvait resservir un `fr.json` périmé même après un `killsw`. Côté SW : handler **network-first** sur `lang/*.json` (timeout 2,5 s + fallback cache `ignoreSearch` pour l'offline).

**Lissage du swap SW passif (v1.47.0).** Quand un nouveau SW prend la main **sans reload** (activation auto au lancement), le 1er boot a pu charger un dico périmé → libellés humanisés. Un handler `controllerchange` (`main.js`, guard « une fois ») appelle **`I18n.reload()`** puis re-traduit **en place** (`_retraduireI18nDomEnPlace` = `_applyI18nDom` + re-render du perf preset, helper partagé avec le sélecteur de langue) → correction à la volée, **zéro flash, zéro reload**. L'update *manuel* (`interfaceMaintenance.js`) reload déjà la page. Couverture = celle d'une bascule de langue (data-i18n + abonnés `onChange`) ; le contenu rendu en JS non abonné (cartes plan…) se corrige au prochain rendu.

## ⚠️ Pièges

- **HTML dans les valeurs** : OK, les valeurs sont insérées dans `innerHTML` (`<strong>`, `<kbd>`, `<br>`, `<span style>` autorisés). Échapper les `"` en `\"` dans le JSON.
- **Ne pas appeler `I18n.t()` au top-level d'un module** (au load) : les dicos peuvent ne pas être encore chargés. L'appeler au moment du rendu (ouverture de modale, build d'innerHTML) — c'est toujours après `init()`.
- **Course au boot (v1.68.1) — « rendu » ≠ « après init »** : le `window load` et le `DOMContentLoaded` peuvent GAGNER la course contre le fetch des dicos (mesuré : dicos prêts à ~700 ms, rendus home*/refonte à ~650-695 ms). Tout rendu déclenché par ces événements (modules home* B7, fallback `DOMContentLoaded` de refonteInterface, bloc résiduel d'index.html) doit passer par la **barrière `I18n.init().then(render)`** — la promesse est **mémoïsée** (`_initPromise`, langManager) donc l'appel est gratuit et sans double-fetch. Sinon : texte « humanisé » gravé dans le DOM (les tooltips du header refonte ne se reconstruisent JAMAIS — early return si `_headerEl`).
- **Garde « retour === clé » MORT depuis l'humanisation H1 (v1.46.x)** : `t()` ne retourne plus jamais la clé brute → tout pattern `const v = t(k); if (v !== k) …` prend TOUJOURS la branche traduite, même clé absente/dico pas chargé (c'est comme ça que « Auto » humanisé écrasait la description FR du preset perf). Le test correct est **`I18n.has(clé)`** (présence réelle, sans warn ni humanisation). Corrigés en v1.68.1 : `_homeT` (homeLoader), desc perf (index.html), `_t` (profileAchievements, shortcutsCheatsheet), `nom` (profileGamification), `t` local (proLicense — qui tourne AUSSI au boot, contrairement à son commentaire d'origine). **Ne pas réintroduire le pattern.**
- **Parité des clés** : vérifier `Object.keys(fr).length === Object.keys(en).length` et qu'aucune clé appelée n'est absente (script de check dans le commit v1.45.0).
- **Pas de jargon dans `version.json > notes`** : l'i18n est invisible à l'user tant que FR est actif → la note user reste simple (« passage multilingue, rien ne change en français »).

## 🏷️ Les infobulles du mode carte ne sont pas re-traduites à chaud — et c'est sans effet

**Constat D36 de l'audit ergonomie du 13/09/2026** : les `title` du mode carte (26 dans `interface.js` et `refonteInterface.js`) sont résolus **à la construction** de l'interface. Un changement de langue à chaud ne les repasse pas.

**Décision KARMA (14/09/2026) : ne rien faire, et écrire pourquoi.**

Le défaut est réel dans le code, mais **injoignable pour l'utilisateur** : depuis la v1.85.4, le sélecteur de langue a quitté l'écran des Réglages. Il ne vit plus qu'à **deux endroits, tous deux hors plan** — `#loaderAppLang` dans ⚙️ Configuration de l'accueil, et l'écran de déverrouillage (`unlockGate.js`). Changer de langue impose donc de quitter le plan ; au retour, l'interface du plan est reconstruite, infobulles comprises.

**Ce qui rouvrirait le sujet** : remettre un sélecteur de langue atteignable depuis un plan. `scripts/check-portee-reglages.js` §7 l'interdit déjà dans `interfaceConfig.js` (`I18n.setLang(` et `cfg_app_lang` y sont refusés au commit). Si un jour la langue redevient changeable en mode carte par un autre chemin, il faudra **traiter les 26 infobulles en même temps** — pas après.
