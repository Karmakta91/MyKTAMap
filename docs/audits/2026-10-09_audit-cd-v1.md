## En une phrase

Le déploiement est **sûr pour les données** (Git hors du dossier web, `data/` jamais touché, refus si un fichier a
été modifié à la main, retour arrière par commit) mais **muet** : rien ne vérifie ce qui est réellement servi après
coup, rien ne signale que la prod a pris du retard sur `main`, et le site de dev publie toute la documentation
interne d'un dépôt privé.

## 💪 Ce qui tient

| Domaine | Ce qui existe |
|---|---|
| **Données** | `data/` hors du *sparse checkout* et `sparse.expectFilesOutsideOfPatterns` posé ; contrôle `verifier_data` qui **arrête** le déploiement si Git se met à suivre un fichier de `data/` (testé le 07/10 sur une copie) |
| **Dossier web** | Dépôt Git **hors** du dossier servi : aucun `.git` exposé. [Certain] `/.git/HEAD`, `/CLAUDE.md` renvoient la page de l'app, pas le fichier |
| **Prod réduite** | En prod, `docs/` se limite à `docs/applications/` : `docs/RELEASE_GATE.md`, `docs/audits/` ne sont pas servis [Certain] |
| **Garde-fous** | Refus si un fichier du site a été modifié sur le serveur ; confirmation `PROD` tapée ; archive de l'ancien site à la première installation |
| **Retour arrière** | `deploy-prod.sh <commit ou tag>`, le commit précédent est affiché après chaque mise à jour |
| **Cache navigateur** | `sw.js` et `version.json` en `no-cache, no-store, must-revalidate` sur les deux sites [Certain] ; `CACHE_NAME` = version servie [Certain : v2.10.2 en prod, v2.10.3 en dev] |
| **Amont** | `merge-main.ps1` n'avance `main` qu'avec garde-fous, Sonar et CI verts ; `release.yml` crée la Release au bump ; `docker.yml` attend la CI du commit taggé (`infra-versioning.md` §29bis) |

## ⚠️ Points faibles

| # | Faiblesse | Risque concret |
|---|---|---|
| F1 | **Le dev publie `docs/` en entier**, sans authentification : BACKLOG, audits, porte de release, architecture (dont `infra-versioning.md` : chemins du VPS, fonctionnement des déploiements). [Certain] `https://dev.myktamap.fr/docs/BACKLOG.md` répond le fichier | Le dépôt est **privé**, mais sa documentation interne est en ligne. Ce n'est pas un relevé (règle `data/` respectée), c'est une carte de l'outillage et des points faibles connus |
| F2 | **Écart prod / `main` invisible** : `main` est en v2.10.3 depuis le merge du 09/10 à 02 h 27, la prod sert v2.10.2 [Certain]. Rien ne le signale | `main = déployable` n'implique pas `main = déployée`. Une release « faite » peut rester des jours hors ligne sans que personne ne le voie ; à l'inverse un correctif urgent peut être cru en ligne |
| F3 | **Aucune vérification après déploiement** : les scripts s'arrêtent sur « en ligne : <commit> ». Ni lecture de `version.json` servi, ni contrôle des en-têtes, ni du `CACHE_NAME` | Une conf nginx modifiée (en-têtes `no-cache` perdus) figerait les clients sur l'ancienne version **sans erreur**. Piège : toute adresse inconnue répond `200` avec la page de l'app — un contrôle doit lire le **contenu**, pas le code HTTP |
| F4 | **Le dev se déploie même CI rouge** : `deploy-dev.sh` pose `origin/Karma_dev` sans regarder la CI. La prod n'a pas ce contrôle non plus, mais `main` n'avance que par `merge-main.ps1` (qui l'exige) — tant que personne ne pousse `main` à la main (pas de protection de branche, cf. BACKLOG) | Un commit refusé par la CI part quand même sur le site de test |
| F5 | **Mise à jour non atomique** : `git checkout` réécrit les fichiers en place pendant que nginx sert. [Probable] Un Service Worker qui s'installe pendant ces quelques secondes peut précacher un mélange ancien / nouveau | Rare (fenêtre de quelques secondes), mais le symptôme serait une app à moitié à jour jusqu'au bump suivant ; `killsw.html` le répare |
| F6 | **Ni journal ni verrou** sur le VPS : aucune trace de qui a déployé quoi et quand ; deux déploiements simultanés ne sont pas empêchés | Diagnostic d'incident à l'aveugle ; course entre deux sessions SSH |
| F7 | **Retour arrière jamais exercé côté clients.** Lecture du code [Probable] : un retour à un commit plus ancien fait **descendre** `version.json` — `updateChecker.js` le détecte (« downgrade ») et **n'affiche rien** ; le `sw.js` différent s'installe (`skipWaiting` + `clients.claim`) et l'`activate` **supprime** le cache de la version retirée : les clients basculent sans le savoir au prochain contrôle du SW. Le correctif suivant doit porter un numéro **supérieur** à la version retirée (règle « on ne redescend jamais un numéro ») | Mécanisme plausible mais jamais joué ; la procédure n'est écrite ni dans `RELEASE_GATE.md` ni dans le journal d'incident |
| F8 | **Une seule clé SSH** lit le dépôt pour les scripts de déploiement et pour le clone qui sert le front pro. [Supposition — à vérifier] Qu'elle soit bien en **lecture seule** (*Settings → Deploy keys*, « Allow write access » décoché) | Si elle a le droit d'écrire, un VPS compromis peut pousser sur le dépôt, `main` compris (pas de protection de branche) |
| F9 | **Scripts en deux copies** (poste de KARMA et `/data/scripts/`) sans contrôle d'égalité — déjà au BACKLOG (« scripts de déploiement versionnés », à trancher) | Une correction faite d'un côté seulement ; on teste une copie et on lance l'autre |

**Hors périmètre, pour mémoire** : `data/index.json` publie l'empreinte du mot de passe d'instance (`accessHash`).
C'est le fonctionnement voulu d'une porte côté client (`security-legal.md`) : elle protège contre le passant, pas
contre quelqu'un qui teste des mots de passe hors ligne. Ce qui la rend solide, c'est un mot de passe long.

## 🔁 Déploiement automatique — décision en attente

Proposé à KARMA le 09/10, non tranché : **dev seulement**, le VPS vérifie lui-même toutes les 2-5 min si
`Karma_dev` a bougé **et** si sa CI est verte, puis lance `deploy-dev.sh` (rien d'ouvert sur le VPS, aucun accès au
VPS confié à GitHub). Il réglerait F4 pour le dev. La prod reste un geste manuel (`PROD` tapé) après la porte. Les
alternatives écartées en première lecture : un webhook GitHub (un service à exposer, contraire à « pas de
backend »), un déploiement SSH depuis GitHub Actions (clé d'accès au VPS stockée chez GitHub).
